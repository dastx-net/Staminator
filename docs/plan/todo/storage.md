# База данных и хранение

Нужно решить, нужна ли приложению база данных. Если нужна, основной кандидат — SQLite.

**Предложение:** хранить в SQLite результаты и события прохождений, а уроки оставить отдельными JSON-файлами. Так уроками будет удобно обмениваться, а историю — анализировать. Настройки окон и оформления тоже могут храниться отдельно; место хранения ещё нужно выбрать.

Вопросы: как переносить профиль и историю на другой компьютер, нужны ли резервные копии и как обновлять формат данных при изменениях приложения?

## Аналитика первой очереди

**Оригинал:** `User.cpp` и `Options.cpp` хранят настройки по профилю в INI, `Progress.cpp` пишет историю по профилю и раскладке. `Stamina.cpp::StopGame` записывает историю только для фраз и файла при длительности не менее 120 секунд; новые требования к аналитике могут отличаться, но это отличие должно быть явным.

**Сейчас:** `apps/desktop/src/user_store.rs` хранит профили и до 10 000 результатов на профиль в одном JSON, переписывает файл при изменении и использует временный файл и резервную копию при замене. Настройки клавиатуры отдельно; позиции книг и геометрия по профилю отсутствуют. Автоматически считать текущий JSON SQLite нельзя.

**Предлагаемое решение:** SQLite для профилей, результатов, настроек и позиций файлов; уроки остаются JSON-файлами. Вынести интерфейс хранилища в `crates/stamina-data`, UI не должен выполнять SQL. Таблицы `profiles` (стабильный ID, имя), `settings` (profile_id, ключ, версионированное значение), `sessions` (ID, profile_id, режим, раскладка, время, верные, ошибки, длительность, причина завершения), `book_positions` (profile_id, идентичность файла, кодировка, смещение). Включить внешние ключи, индексы по профилю и дате; результат и позицию сохранять одной транзакцией при принятии результата. Сохранять исходные счётчики, а производные метрики вычислять по документированной формуле. События каждой клавиши в первой очереди не собирать: это отдельное решение для [журнала](session-log.md).

Версию схемы хранить в `PRAGMA user_version`; миграции запускать последовательно в транзакции, неизвестную новую версию не перезаписывать. Однократно импортировать существующий `profiles.json` с сохранением ID и результатов, проверкой количества и резервной копией исходника; при ошибке откатить транзакцию и оставить JSON. Политика записи результатов первой очереди: сохранить текущее поведение приложения, а фильтр совместимости с оригиналом определить отдельно после сравнения. Пользовательские уроки хранить вне базы. Для переноса предусмотреть экспорт целого набора данных в отдельной задаче; до него документировать закрытие приложения и копирование каталога данных, включая пользовательские уроки. Для резервной копии работающей SQLite использовать её backup API, не копировать отдельно живой файл при WAL.

**Приёмка:** миграция копии JSON сохраняет профили и результаты и повторный запуск не дублирует их; сбой миграции не повреждает источник. Проверить раздельность профилей, транзакционный откат, восстановление из резервной копии, отказ записи и неизвестную версию схемы с понятной ошибкой. Решить расположение каталогов и фактическую политику истории до реализации миграции.
