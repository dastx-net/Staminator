# Автоматизация issue

Бот берёт issue из GitHub и доводит до pull request через Codex. Работает на домашнем сервере easy-day под отдельной учёткой `stamibot` (без sudo, docker и libvirt).

## Когда бот берёт issue

- Issue открыт в `dastx-net/Staminator` и назначен на `losinkatorf`.
- Назначил доверенный инициатор: `DanielSanIT` или сам `losinkatorf` (список `initiators`).
- Расход лимита Codex меньше 75%. Проверка идёт перед каждым ходом Codex. Если лимит выше, бот пишет в issue и ждёт сброса.

Issue, назначенный кем-то другим, бот игнорирует. Комментарии посторонних в промпты не попадают.

## Стадии

| Стадия | Кто | Что делает |
| --- | --- | --- |
| `plan` | `gpt-6-sol` | Пишет план в `.stamibot/plan.md` |
| `plan_review` | `gpt-6-astra` | Ревью плана. P0/P1 возвращают план на доработку |
| `implement` | `gpt-6-sol` | Реализация и локальные проверки. Коммит делает бот |
| `impl_review` | `gpt-6-astra` | Ревью диффа. P0/P1 возвращают на доработку |
| `ci_push`, `ci_wait` | бот, Jenkins | Push ветки, ожидание результата сборки |
| `e2e` | `gpt-6-sol` | Запускает собранный `.exe` в Windows VM, смотрит на экран, проверяет изменение |
| `pr` | бот | Открывает pull request, пишет ссылку в issue |
| `pr_open` | бот | Следит за pull request и issue, ждёт замечаний |
| `done` | бот | Pull request смержен или закрыт. Ещё 14 дней (`followup_days`) бот следит за новыми комментариями |

- На любой стадии Codex может задать вопросы. Бот публикует их комментарием и ждёт ответа инициатора в issue.
- Ревью крутится в цикле, пока остаются замечания серьёзнее P2 (P0, P1). Ограничения по числу кругов нет (`max_review_rounds` = 0), цикл останавливает только лимит Codex. P2 и P3 остаются открытыми и попадают в описание pull request.
- Лимит починок CI: 3. Дальше бот останавливается (`blocked`) и пишет причину. Продолжить: комментарий `/retry` с необязательными указаниями.
- Упавший CI возвращает задачу на `implement` с хвостом лога.
- Закрытие issue или снятие назначения до открытия pull request отменяет работу.
- Ветку с правками в защищённых путях (`protected_paths`: `automation/`, `.github/`, `.cargo/`) бот не пушит и останавливается. `/retry allow-protected` разрешает push именно этого коммита. Любой другой `/retry` возвращает задачу на `implement` с требованием отменить эти правки.

## Замечания после открытия pull request

Учитываются замечания доверенных инициаторов: ревью с текстом (`Request changes` или `Comment`), построчные комментарии, комментарии в pull request и новые комментарии в issue.

- Pull request открыт: новый круг `implement`, `impl_review`, CI, пуш в ту же ветку. Бот отвечает в pull request, что сделано. На вопрос отвечает текстом без правок кода.
- Pull request смержен или закрыт (`done`): бот создаёт ветку `issue-N-followup-K` от `master`, проходит тот же круг и открывает новый pull request.
- Вопросы Codex на этих кругах бот задаёт в pull request, если он открыт, иначе в issue.
- Комментарий, пришедший во время работы, не прерывает ход Codex: бот подберёт его, когда вернётся к слежению.
- Комментарии бота помечены `<!-- stamibot -->`: так он отличает их от ответов человека (пишет от имени `losinkatorf`).

## Как бот узнаёт о событиях

Опрос GitHub API раз в минуту: `stamibot.timer` запускает `bot.py tick`. Сервер стоит за NAT, вебхуки не нужны. Один запрос в минуту на список issue, по одному на каждый открытый pull request бота и по два на каждый недавно завершённый issue. Комментарии читаются только при изменившемся `updated_at`. Issue обрабатываются по очереди.

## Размещение на easy-day

| Путь | Что |
| --- | --- |
| `~stamibot/stamibot/bot` | Клон репозитория с кодом бота (ветка `master`) |
| `~stamibot/stamibot/repo`, `wt/issue-N` | Рабочий клон и worktree на каждый issue |
| `~stamibot/stamibot/state/issue-N` | Состояние и логи ходов Codex |
| `~stamibot/.config/stamibot/gh-token` | Токен GitHub, режим 600 |
| `~stamibot/.config/stamibot/config.json` | Переопределения настроек из `DEFAULTS` в `bot.py` |
| `/srv/data/staminator-ci` | Результаты CI (`results/<sha>.json`), сборки Windows (`artifacts/<sha>`), кеш cargo |

Сеть: всё идёт через прокси A&D `127.0.0.1:18888`, кроме GitHub, OpenAI и crates.io (как в devuw).

Команды под `stamibot`:

```bash
python3 ~/stamibot/bot/automation/issuebot/bot.py status   # стадии issue и расход лимита
journalctl --user -u stamibot.service -f                   # журнал
systemctl --user stop stamibot.timer                       # остановить опрос
git -C ~/stamibot/bot pull                                 # обновить код бота
```

## CI в Jenkins

Задача `staminator` на Jenkins easy-day (`http://192.168.1.98:8080`) опрашивает GitHub раз в минуту и собирает каждую новую ревизию любой ветки. Pipeline хранится в конфигурации задачи; копия лежит в `automation/ci/jenkins-job.xml`. `Jenkinsfile` в ветке ничего не значит.

1. Собирает образ `staminator-ci:<версия>` из `automation/ci/Dockerfile` ветки `master`. Версию Rust берёт из `rust-toolchain.toml` собираемой ветки; допустим только номер вида `1.99.1`.
2. Скачивает зависимости: `cargo fetch --locked` в сети Docker `staminator-ci`. Код ветки на этом шаге не выполняется.
3. Запускает `automation/ci/run.sh` собираемой ветки в контейнере без сети: UTF-8, fmt, clippy, тесты с покрытием 95%, сборка `x86_64-pc-windows-gnu`.
4. `automation/ci/report.py` из `master` кладёт результат в `/srv/data/staminator-ci/results/<sha>.json`. Бот читает этот файл: учётка Jenkins ему не нужна.

### Граница доверия

Ветка считается недоверенной: её пишет Codex, а он читает issue, зависимости и веб.

- На хосте выполняется только pipeline из задачи и файлы `automation/ci` из `master`. Агент Jenkins состоит в группе `docker`, то есть равен root на сервере.
- Код ветки работает только в контейнере: без сети, без `.git`, без привилегий (`--cap-drop ALL`, `no-new-privileges`), с лимитами памяти и числа процессов. Видит свою копию дерева, кеш зависимостей на чтение и кеш сборки своей ветки.
- Кеш сборки отдельный на ветку (`cache/targets/<ветка>`), новая ветка получает копию кеша `master`. Каталоги старше 14 дней удаляются.
- Из `ci-out` публикуются только обычные файлы `.exe`; ссылки пропускаются.
- `master` защищён на GitHub: изменения только через pull request, без force push.
- Сеть `staminator-ci` (`172.31.250.0/24`) отрезана от хоста, домашней сети и VM правилами из `automation/ci/host-firewall.sh`. Скрипт запускают один раз под root.

Изменение pipeline: поправить `automation/ci/jenkins-job.xml`, после слияния в `master` применить файл к задаче (способы указаны в его заголовке).

## End-to-end в Windows VM

После зелёного CI Codex проверяет сборку в VM `ad-teams-win11` через `automation/e2e/vm.py`:

- Экран и ввод идут через VNC-консоль VM (`127.0.0.1:5900` на easy-day, `vncdotool` в `~stamibot/stamibot/venv`). В гостевой системе для этого ничего не установлено.
- Тесты идут на рабочем столе отдельного пользователя Windows `e2e` (обычный, не администратор, без входа в Teams). Он входит автоматически при загрузке VM; пароль лежит в `~stamibot/.config/stamibot/vm-e2e-password` и в реестре VM (автовход).
- Файлы и команды идут по SSH под администратором (`igor@192.168.123.60`, ключ `~stamibot/.ssh/win11_vm`). Программа стартует на рабочем столе `e2e` через задачу планировщика `stamibot-e2e`.
- Codex делает снимок (`vm.py shot`), смотрит PNG, кликает и печатает (`click`, `type`, `key`). Команды: `vm.py --help`.
- Провал e2e возвращает задачу на `implement`. Результат попадает в описание pull request.

Стадия пропускается с пометкой в pull request, если VM выключена, пользователь `e2e` не вошёл в систему или VM занята по RDP. Бот никогда не отбирает VM у активной RDP-сессии. Когда RDP закрыт, бот сам выводит рабочий стол `e2e` на консоль (`vm.py console`); сессия `igor` при этом остаётся запущенной.

Windows 11 Pro держит одну активную сессию: при входе `igor` по RDP сессия `e2e` отключается, Windows может спросить подтверждение.

## Ограничения

- В VM нет наследуемых данных `src/stamina_setup` (фразы): e2e проверяет встроенные уроки из `lessons`, которые Codex копирует рядом с `.exe`.
- Одобрение (`Approve`) и ревью без текста бот не обрабатывает. Мержит человек.
- Codex и токен GitHub работают под одной учёткой, сеть у Codex включена. Codex может прочитать токен, ключ SSH и пароль тестовой VM. Изоляция держится на отдельном пользователе и списке доверенных инициаторов. Токен должен быть fine-grained: один репозиторий, права Contents, Issues и Pull requests, без Workflows и Administration. План разделения учёток: [docs/plan/todo/automation-hardening.md](../docs/plan/todo/automation-hardening.md).
- Каталог `/srv/data/staminator-ci` открыт на запись всем локальным пользователям (на сервере нет `setfacl`); `results` и `artifacts` пишет только агент Jenkins.
